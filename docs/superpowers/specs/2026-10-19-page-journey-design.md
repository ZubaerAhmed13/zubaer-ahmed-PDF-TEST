# DocFlow dedicated-page journey

Approved direction: the 19 October UI research proposal, followed by the user's explicit instruction to start the upgrade. Implement in the existing application on an isolated feature branch.

## Outcome
All 29 tools receive an addressable page: choose tool → select files → preview/configure/edit → process → separate result/download page. Browser navigation and return to editing preserve the current in-tab workspace. English, coral/navy identity and current tool IDs remain.

## Design
- Compact homepage with immediate search and popular tools; secondary settings in an accessible menu.
- Tool page has its own heading, three-stage indicator, focused upload state, relevant quality/privacy guidance and the real existing input.
- Mounted workspaces keep their PDF engines and lifecycle. Use the existing dialog element only as a nonmodal page container with region semantics, so legacy adapters retain their integration point. The page is not a focus-trapping modal.
- Desktop retains generous canvas/panels. Phone uses compact navigation, reachable actions, 44px primary targets and contextual settings, with no shell overflow.
- Output events capture exact generated bytes into a bounded result owner. Show filenames, exact size, rename, download/share, return to editor and applicable preview/continue actions. Never silently rerun an operation.
- Multi-output and incremental batch outputs retain distinct identities. Cancelled, failed or stale operations cannot publish a current result. Changes invalidate prior result navigation.
- URLs contain stable tool IDs or opaque result IDs only. Expired result deep links show an honest recovery screen.
- Browser Back/Forward respects leave guards; a rejected navigation restores its history entry. Direct links work on GitHub Pages using hash routes.

## Processing policy
Backend processing is authorised where demonstrated quality/resource benefits justify it. This UI release preserves the working local operations and makes no universal future local-only promise. No fake server controls or undeployed remote-processing capability. Heavy workers and their temporary-storage/queue/cost contract form a subsequent capability increment after a measured engine benchmark; Supabase Edge CPU limits rule out assuming it is a heavy PDF runtime.

## Acceptance
All stable tools load through new pages. Verify true PDF output and download on a separate result page, exact output identity, rename, return to unchanged editing state, invalid/stale result links, navigation rejection, mobile overflow and keyboard/axe checks. Existing unit/PDF/browser suites remain regression gates; migrate modal-specific selectors and result navigation expectations to the new public behavior without weakening output assertions. No runtime dependency or host change.
