# Form filling v2 acceptance

The form tool now inspects the actual AcroForm and offers labelled controls beside the PDF plus matching page widgets. JSON is absent from this user flow. Supported controls include text/multiline fields, checkboxes, radio groups, dropdowns (including editable single-value dropdowns), single-select lists and multi-select choices. Read-only controls are disabled. Required-field validation opens phone settings when needed and waits for visibility before focusing, while respecting a newer user focus. Page jumps focus the corresponding widget. Crop/rotation/zoom geometry uses the rendered PDF.js viewport and the canvas's exact position.

Values remain in the current document draft through page navigation and Back/Forward. Replacement/reset clears them. Export sends only modified fields to the existing worker, preserving untouched values and appearances. Page controls use browser styling; exact PDF typography is assessed in the exported-byte review. Their opaque background prevents old values showing through, and zero control margins preserve widget alignment. Flattening remains explicit. Flattened output is independently reopened to confirm that the AcroForm and widget annotations are removed.

Review found four real choice defects: numeric radio appearance states could be confused with export choices; display labels could overwrite separate export codes; multi-select dropdowns could lose selections; single-select lists could silently become multi-select. Radio inspection records the real widget/export association, choice multiplicity is carried through controls and the worker rejects illegal multiple selections.

30 October choice fidelity round: paired choice labels/export codes are supported for dropdowns, editable single-value dropdowns and lists when labels/codes are unique and nonempty. Controls display readable labels and store actual codes in the draft. The worker writes validated codes to `/V`, numerical option indices to `/I`, and generates visible label appearances without replacing actual values or changing `/Opt` or field flags. Clearing removes old values/indices. Untouched appearances remain unchanged; missing read-only appearances are regenerated using labels. Editable suggestions map labels to codes and custom text remains available; blur resolves a typed code to its visible label so both controls agree. Paired choices with repeated/empty labels or codes and editable multi-select dropdowns fail clearly in both UI and worker. These shapes need an index-based editor to avoid ambiguous mapping.

Fresh review reproduced a missing selection highlight for long labels that wrap. The list renderer now tracks each line's originating option instead of comparing line text, preserving all selected wrapped rows without highlighting identical fragments in other options. A failing-then-passing regression and independent editable/flattened pixel checks cover this. Styled, sorted lists at all four widget rotations are pixel-identical to the compatible default-rendered reference corpus.

Nine browser journeys reopen editable and flattened PDFs, check read-only values, required fields, cropped/rotated widget bounds, zoom, numeric radio mapping, unchanged multiple selections, editable dropdowns, single-select flags, page jumps, phone focus and intentional-focus preservation, XFA rejection and source replacement. Choice-policy units first failed before the mapping/unsupported-form guards. Resource probes first failed before the field-control fan-out limits. The historical release fixture now explicitly enables multi-selection when testing two selected values, rather than relying on an implicit mutation of its PDF flags.

UI limits: 250 fields, 200 choices per field, 1,000 widgets, 5,000 combined sidebar choices and 20,000 choices repeated across widgets. These bound control creation; they are not certified heap or physical-device capacity limits. XFA and unsupported choice shapes fail clearly. Text support and appearance fidelity depend on the source/default PDF fonts; unsupported characters can fail at export. Cryptographic signature validity is not preserved by rewriting.

The prior published source passed 85 v2 Chromium journeys and 216 units. This round adds eleven units (227 total), typecheck/lint/build/provenance and independent PyMuPDF 1.26.6 verification of 12 PDFs: actual codes, numerical indices, readable text, selected-row/wrapped-row pixels, four-rotation style parity and flattened widget removal. The browser choice journey now selects labels, syncs sidebar/page controls, returns to editing and reopens real editable/flattened output. Current-head three-browser CI is required separately. Local browser QA is unavailable through the managed `http://terminal.local` preview because that insecure context does not expose `crypto.randomUUID`, which the existing shell requires; no production code or browser security setting was weakened to hide that limitation. Broader font/document fidelity, physical devices, manual assistive technology and memory stress acceptance remain open.

The same input-boundary review reproduced an unrelated output corruption: an untouched field named `constructor` inherited a JavaScript prototype property and was rewritten. Only own submitted properties now count as edits, and non-object value payloads are rejected. The regression was observed failing before the fix.

The same follow-up makes workflow file names readable, keeps per-file states visible while collapsing repetitive preservation details, and labels queue completion independently of document success. A separate Vercel static-preview package preserves the existing nested asset/service-worker path and records the exact Git commit. Production promotion remains gated separately.
