# OCR workspace acceptance

Device OCR uses the existing on-device Tesseract engine and same-origin English/German models. This mode uploads no document. It offers language/mixed-language recognition, selected pages, a one-to-thirty-page run limit, existing-text skipping, rotation/deskew/cleanup previews, cancellation, preserved settings, searchable PDF/text downloads and review of the actual resulting PDF. Input metadata is capped at 40 MB before reads. Unprocessed pages remain unchanged and are listed for retry from the original.

Corrections affect recognition input; the invisible text layer maps back onto the source scan. OCR may be wrong, is not tagged-document/accessibility certification, and rewrites invalidate existing digital signatures. The small fixed corpus and hosted synthetic OCR checks do not establish broad accuracy for difficult scans.

At source `1a865b2`, all four added OCR browser cases passed in Chromium, Firefox and WebKit: real scan recognition, preserved unprocessed pages/settings, correction validation and deferred previews rejected after settings change. Complete v2 counts were Chromium 89, Firefox 88 and WebKit 88, with one browser-specific skip. Quality and processing CI also passed. Full legacy/browser/device acceptance remains open.

## Explicit server mode

Source `67fca54` adds server OCR only when `VITE_DOCFLOW_SERVER_PROCESSING=1` and public Supabase configuration are present. Device mode is the default. Server mode requires a confirmed DocFlow account and fresh consent naming Supabase/Vercel, whole-document processing, 25 MB/100-page/180-second staging limits, 30-minute output expiry, five-minute cleanup and two-hour signed-upload lifetime. Local-only page/correction fields are disabled in server mode. No automatic upload or local-to-server fallback occurs.

Account tokens remain tab-scoped. Passwords and upload consent never enter option snapshots. Authentication generations prevent late sign-in/refresh from restoring a signed-out session. A failed request retains the source and the same processing attempt. Recovery can check owner-scoped status, retry acknowledged cancellation and retrieve completed bytes without another create/start. Recovery checks and retrieval wait for the original request to settle. Navigation waits for actual terminal acknowledgement, shares a pending cancellation across route requests and rejects disposed output callbacks.

A definite first-response staging rejection can be checked as no job and released. A rejection after a lost first response remains uncertain and retains the original key. Completed server work is reported as completed if it wins cancellation; the local transfer can be stopped without claiming that server work was cancelled.
